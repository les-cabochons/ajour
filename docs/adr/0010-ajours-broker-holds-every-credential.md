# Ajour's broker holds every credential

Plugins never see a secret, not even their own. A broker in Ajour's main process holds every credential in the OS secret store, through Electron safeStorage, and makes every authenticated request. A plugin asks for a connection, a method, a relative path, a query, allowed headers and a body. The broker then:

- builds the URL from the connection's base address;
- checks the manifest's endpoint allowlist;
- refuses private addresses unless the user marked the connection as on-premises: it resolves the host, refuses the request when any address is private, and connects only to the addresses it checked;
- follows same-origin redirects only, and hands a cross-origin redirect back to the plugin;
- attaches the credential;
- removes secrets from what comes back.

Every auth scheme lives in the broker: bearer and basic credentials, header templates, a secret written into a JSON body field, a feed address that is itself the secret, and OAuth with PKCE and a loopback redirect. A secret can also be generated by the broker, so the plugin never sees it at all. A plugin with the sign-in capability only declares the service, its client and what it offers. The broker runs the sign-in and holds the account. Another plugin uses that account only through a grant the user approved, for what that plugin declared. The broker sits behind a message-shaped port, so a separate credential agent could replace it later. The full model is on #229.

## Considered options

- **The plugin runs its own sign-in, and Ajour stores an opaque credential.** This was charted first, then rejected: the plugin would hold the refresh token, and ADR 0007 forbids plugin code from holding any credential.
- **Microsoft and Google sign-in built into Ajour only.** Rejected. Ajour would ship every client registration, and each new service would need an Ajour release. A built-in sign-in, such as a possible Ajour account, uses the same declaration as a plugin's, so either path stays open.
- **WAM through MSAL on Windows, now.** Deferred. MSAL's native broker does its networking outside the broker's stack, creating it keeps Node from exiting (MSAL #7076), and a draft MSAL change removes desktop support (MSAL #8836). Until it returns, organisations that require device-bound tokens can't use Microsoft sign-in.
- **The host hands the plugin a token for each call.** Rejected. The token would sit in plugin memory, and any request could carry it away.

## Consequences

- The rule in `docs/agents/architecture.md` that a plugin owns its external-system authentication and transport is reversed. A plugin owns its requests and its data mapping. Ajour owns credentials and transport.
- Secret connection fields are never passed to a plugin and never accepted back from one. On first run, existing secrets move from the state file to safeStorage. When encryption is unavailable, Ajour refuses to store secrets and says so.
- Accounts belong to the plugin that declared their sign-in. Uninstalling that plugin removes its accounts and every grant on them.
- An update that widens a plugin's access starts disabled until the user approves it again.
- The local API stops accepting unauthenticated loopback callers (#232).
- The broker uses Electron's network stack, for the system proxy, PAC files, the OS trust store and Windows integrated sign-in. That stack can't be told which address to connect to, so a request the broker reaches directly goes through a CONNECT tunnel of its own on loopback, which connects only to the addresses the broker checked (#434). TLS still runs between Chromium and the service, on the name. A name that rebinds after the check can't move such a request.
- What the broker doesn't pin is judged by the address that answered, after the request was sent: a request through a system proxy, where the proxy connects, and an address literal, which can't rebind. A DNS-rebinding window remains there: when a PAC file falls back to `DIRECT`, a name that rebinds between the check and the connection reaches its new address, and only the answer is refused. It cannot break G1, because credentials attach only to hosts the user configured. The answering address has two more gaps, recorded on #389: through a system proxy the proxy answers, so only an answer from an address that isn't a proxy's is judged; and when the stack names no answering address, only the first check holds, and the request's event says so. A third is a name only the proxy can resolve: when this computer's resolver has no address and a proxy answers for the name, the broker refuses names that are not public domain names (a single label, `.local`, `.internal`, `.lan`, `.home.arpa`), but a public-looking name such as `127.0.0.1.nip.io` passes, and the proxy then connects to wherever it resolves it. A denylist of wildcard-DNS names is not robust, and refusing every name this computer can't resolve would break the proxies that exist to resolve them, so this stays a stated limit. The first address of a connection is one the user entered; the exposure is a redirect from a service the user chose, through the user's own proxy, which keeps its own policy.
- The Vault page lists every secret Ajour holds, but never shows or copies a value. A secret meant for other people, like a team secret, is shown once when it's created or rotated.
- G2 stays best effort: a plugin can still misuse what its grant allows.
