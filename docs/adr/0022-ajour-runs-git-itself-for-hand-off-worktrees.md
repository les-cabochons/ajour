# Ajour runs git itself for hand-off worktrees, and keeps them inside the repository folder

Every hand off of a project started in the same repository folder, so two coding tools working on two backlog items edited one checkout. Ajour now makes a git worktree for the item and starts the tool in it (spec #857, first built in #860). Something has to run `git worktree add`, and until now nothing in Ajour's own code ran git.

ADR 0019 covers plugins only: a plugin asks the process broker for a command, behind the user's consent, the gates and the command mode. That path doesn't fit here. A worktree is made before any tool is asked, for every tool alike, and its folder is one a plugin may never name. So Ajour's local API runs git itself, in one module, `apps/api/src/worktrees.ts`. Nothing else in Ajour ran git until Deck's local clones ([ADR 0023](0023-ajour-fetches-pull-requests-into-the-users-clone-with-the-users-git-setup.md)), which run it under the same rules through the same runner, now `apps/api/src/git-process.ts`.

**The rules of every git call.**

- No shell. Git gets an argument list, with `--` before every path.
- A ref that starts with `-` is refused, and a branch name passes the hand-off branch check plugins' `ref` arguments pass.
- The environment is the one the process broker gives a git child: the user's, without `AJOUR_` variables, with `safe.bareRepository=explicit` and `GIT_OPTIONAL_LOCKS=0` (`gitEnvironment`). The module reuses the broker's functions and adds `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`, so git fails where it would ask for a password. On POSIX git runs in its own session, without a terminal to prompt on.
- Each call has a timeout: 15 seconds for a call on refs, 20 for a fetch, 120 for a checkout. A call that runs out is stopped with everything it started, and settles at that moment whatever still holds git's output. Once git exits, the call waits at most a second for the rest of its output: a hook's background child or a helper can inherit that output and keep it open, and the call must not hang on it while it holds the repository's lock.
- Writes to one repository run one at a time, keyed by its common git folder, so two hand offs never pick the same name.

**Where worktrees live.** Always at `<repository folder>/.ajour/worktrees/aj-<item key>`, then `-2`, `-3`. An item without a key, such as one made by hand, gets `aj-` and the first 8 characters of its own id, so two such items never share a name and a `-2` always means a second worktree of one item. The user registered that folder, so Ajour writes nowhere they didn't point it. Ajour adds `/.ajour/` to the repository's local exclude file, under its common git folder, so the worktrees never show in git status and no committed file changes. A committed `.gitignore` outranks that file, and one that re-includes folders, such as `*` then `!*/`, would show `.ajour/`, so Ajour also writes `.ajour/.gitignore` holding `*` once `.ajour` is proven a real folder (#857). It never follows a link there and never changes a file already there. A folder that isn't the top of a git checkout, or a computer without git, gets no worktree: the hand off starts in the repository folder, as before.

**What a create does.** It checks the folder, writes the exclude line, fetches the source branch, and then makes three things in order, noting each once it is made: the folder, with a `mkdir` that fails on a name that exists, the branch, with `git branch --no-track` from the source's commit, which fails when the branch exists, and the worktree, with `git worktree add --lock`. Before that it makes `.ajour` and `.ajour/worktrees` as real folders, and refuses when either is a link or a file: a link there, which a cloned repository can even commit, would send the checkout and its removal outside the repository folder. The source is the branch the user picked for that hand off (#861), which must be one the repository has. Without one it is the source they last picked for that repository folder, else the remote's default branch, else the branch checked out in the main folder when there is no remote. A fetch that fails is not fatal: the branch starts from the last fetched copy, and the hand off says so. A source that names nothing refuses the start. The new branch never tracks its source, so a plain push can't target the source branch.

**Taking it back.** Git keeps the worktree locked from the add until the tool has answered, so no prune removes it mid-start. If a step fails, or the tool refuses the start, Ajour removes the folder, the branch and the worktree that create noted as made, and nothing else. A start whose outcome is unknown is the exception (#857): when the plugin timed out, its process ended, its answer was too large or failed validation, the operation was cancelled, as when the user turns the plugin off mid-start, or the tool's error says `mayHaveStarted`, the tool may run in the worktree, so Ajour keeps it, records no handoff and says so in the refusal: a folder or a branch another program made under the same name meanwhile stays. Before it removes anything it checks `.ajour/worktrees` again, and that the folder is still the one it made, by the identity the file system gave it: when a link or another folder holds the name, it removes nothing and leaves it for the user. Whether git's own removal runs follows what `git worktree list` holds, because an add can register the worktree and still fail. Only a worktree listed there on the branch this create made is removed: a branch is checked out in one worktree only, so any other worktree in that folder is another program's, and it stays with its files. The branch goes only while it still points at the commit it started from: a branch that moved holds work, and stays. One start of an item in a repository folder runs at a time, from picking its place until its worktree is kept or taken back, so a second start never joins a worktree the first is about to remove. No prune runs, because it would also drop the user's own worktrees whose folders are away.

**Folder ids and access.** ADR 0019 holds: a plugin gets a folder id, never a path. A worktree has its own id, which the folder resolver resolves to the worktree's path for the worktree's project only, and only while that path is a real directory under its repository folder. The plugin receives that id wherever it received the repository folder's: the start, state reads, Open and Close. A start in a worktree also names the repository folder, by its own id, as `repositoryFolder`. A tool that refuses the start, such as one that won't run in a folder the user never trusted, loses a new worktree at once, so it sends the user to the repository folder, which stays. For access a worktree counts as its repository folder. A remembered command approval is looked up and kept with the repository folder's id, and so are the settings a tool keeps per repository folder. The dialog that asks about a command shows the folder it runs in, a worktree's included, and says that Always covers the repository folder and its worktrees. This widens ADR 0019's "nothing broader" by one step, on purpose: an approval for a repository folder also covers that folder's worktrees, so a new worktree asks for nothing the user already allowed there.

## Considered options

- **Run git through the process broker, as a built-in plugin would.** Rejected. The broker's gates, consent and command mode decide what a plugin may do. Ajour's own worktree needs none of them, and a plugin could then ask for the same commands.
- **Leave worktrees to each tool.** Rejected. One tool makes its own from the branch Ajour sends, and the others work on whatever is checked out. Such a tool declares `ownWorktree` and Ajour makes none for it.
- **Keep worktrees in Ajour's data folder or beside the repository.** Rejected. Tools record trust and settings per folder, and a folder inside the repository the user registered is the place they expect. Ajour's data folder is a protected root no plugin command may run in.
- **Write `.ajour/` into `.gitignore`.** Rejected. It changes a committed file of a repository that isn't Ajour's.
- **A library that speaks git's formats.** Rejected. The user's git, with their credentials and configuration, is what fetches their remotes.

## Consequences

- Ajour's own code now starts a program outside the process broker. The module, and since ADR 0023 Deck's local clones, are the only places that run git, and its tests run real git in a temporary repository through the routes. A worktree's Open in terminal (#862) is the one other start: the local API opens the user's terminal app in the worktree's folder, with the launch a plugin's terminal command already gets and no command of a plugin.
- Git runs with the repository's own configuration and hooks, as ADR 0019 already accepts for a plugin's git: `.git/config` and `.git/hooks` are the user's, never committed. A `post-checkout` hook runs when a worktree is added.
- A test runner, linter or search tool that walks the repository folder may read the copies under `.ajour/worktrees`, although git ignores them.
- A development build protects its own checkout, so it can't be a repository folder. Developers handing off Ajour's own tickets keep mapping another clone.
- Each worktree operation is one wide event with its outcome and duration: `worktree.create`, `worktree.keep` and `worktree.discard`, `worktree.resolve_source` for a tool that makes its own worktree (#863), and since #862 the requests `worktree.status`, `worktree.delete_preview`, `worktree.delete`, `worktree.forget` and `worktree.open`. A clean-up round (#864) is one request event, `worktree.clean_up`. None holds a branch name, a path, a file name or what git wrote (ADR 0011).
- The same module lists the branches a new worktree can start from (#861), for the window's branch finder. That call reads refs only: it fetches nothing and writes nothing.
- The same module reads a worktree's status and deletes or forgets one (#862). A delete takes a worktree's id, never a path. A record made in an earlier session holds no file-system identity, so the proof is git's: the folder is a real directory in `.ajour/worktrees`, git lists it as a worktree of the repository on the branch Ajour recorded, and it is itself a checkout of that repository. Anything else at the path stays. The user confirmed with the list of uncommitted files, so the removal is forced. Just before it, Ajour checks that the worktree still holds what the dialog showed (#857): every untracked file, also one inside a new folder, the commit it is on and the tip of its branch. A change since refuses the delete. A missing worktree's registration is dropped alone: `git worktree prune` never runs, since it would also drop the user's own worktrees whose folders are away.
- For a tool that declares `ownWorktree` (#863) the module makes nothing. It only answers the source a new worktree would start from, fetched first when it is a remote's branch, and the hand off sends that name and the branch name to the tool, which makes the worktree itself. With Main folder the tool gets neither. Ajour doesn't list, delete or clean a worktree a tool made.
- The same module removes worktrees by itself (#864), by two rules the user sets: the worktrees of finished items, and unused ones. The window starts each round, because backlog items live there, and sends when each item became finished. The module decides. A round's removal is the delete above with one difference: nobody confirmed it, so it is not forced. Ajour reads git status under the repository's lock and runs `git worktree remove` without `--force`, so git refuses a worktree with modified or untracked files. It also keeps a worktree with a running thread, a hand off's or one a tool lists in the worktree that no handoff links (#857), in the state the listing gives, since a state read may act on the thread, a hand off or a thread change in the last hour, another branch checked out, or a folder that fails the proof above. Only the round asks for the branch: a hand off into a worktree a tool switched, and a delete the user confirmed, take it on any branch (#857), and the delete's branch box still deletes only the branch Ajour made. It never deletes a branch, and it never removes what git left behind of a worktree it couldn't remove whole. A hand off takes its hold on a worktree under the repository's lock, and a removal takes its last look at the rules, the holds and the threads under the same lock, so the two never cross. `worktree.clean_up` is the round's one event, with counts and no name.
