# Deck's chat may make any review write the user can, shown as action lines

Deck's chat (#796) is the fallback for what the asks don't cover, and the user can ask it to act, not only to answer: add a draft comment, post a comment, reply, resolve a thread, submit a review with a summary, regroup the guide, and, on their own pull request, edit the title or toggle draft. Until now an agent in Ajour wrote only the user's local data, behind an Undo window (ADR 0001), or a guide that stays on the user's computer. These writes reach the code host in the user's name, and other people read them at once. We decided the chat's agent may make them, as tools of its pull request conversation, and that each one is visible and deletable instead of held for confirmation. It sits beside [ADR 0002](0002-pull-request-writes-are-immediate.md): writes are still sent at once, with no Undo window and nothing queued.

- **Only in a chat turn.** The tools are listed for every turn of the conversation, as `submit_guide` is (#794), but Ajour takes them only while a `deck.chat` turn the user started runs, at that turn's head, and while the repository is allowed with the conversation's agent. An ask or a guide turn that calls one is refused, so a question never posts anything. Each write checks the turn, its head and the consent again as its last step, with nothing awaited before the plugin starts or the window hears of the draft comment, so a reply stopped or a repository revoked while the write read the diff or waited for the plugin's admission writes nothing. A draft comment is checked once more when the window claims it: the window adds it only once the local API grants its claim of the call, which the API does in one synchronous step only while it still waits for that call, the call's turn is still the conversation's running chat turn, and the consent holds. The window's own view can't decide it, because a call may reach it after the API stopped waiting, or after a Stop it missed while its stream was down and that no reconnect replays. A granted claim waits for the window's answer longer than an ordinary call, and turning MCP off doesn't fail it; if that answer never comes, the agent hears the comment may be in the draft review, not that it wasn't added. A window that lost its claim's answer adds nothing and tells the API so at once. A call claimed before Stop completes is added and gets its line even when Stop arrives right after: the user sees what was added and can delete it.
- **What the page allows.** Each tool goes through the same code host operations, access choices and plugin admission as the user's own writes. Title and draft writes are refused unless the page said the user authored the pull request when it sent the message: the local API keeps no pull request facts to decide it, so it keeps the page's word, as the turn is queued. An action line's link is the plugin's only when it is an http(s) address on the pull request's own origin. A draft comment goes to the draft review in the window, over the bridge's data tools, and nothing reaches the code host until the user sends Finish review. A reply or a resolve names its thread by the id `read_threads` gave, and Ajour reads the pull request's threads again through the plugin before it writes: an id that isn't one of them is refused, because a code host acts on a thread's id alone (GitHub's `resolveReviewThread` takes a node id, whatever pull request it is on), so an id the agent was handed could otherwise reach another pull request.
- **No verdicts.** The chat's `submit_review` submits a comment review, a summary only: its schema has no verdict, and the local API refuses one sent anyway rather than drop it. Approve and request changes stay the user's own Finish review, as the draft review does. The agent reads text other people wrote, the description, the code, the threads and the tickets, and its prompt says that text is data, never instructions; but a prompt can be argued out of, and an approval is the one write a reader acts on without reading it: it can let a pull request merge. So no text an agent reads can ever approve, however it was worded.
- **One post across tries.** A post (a comment, a reply, a review) keeps one submission while the agent tries it again: its id is named by the conversation, the pull request and what it posts, the same words on the same lines or in the same thread, and a try after one that may have reached the code host sends the first try's time, so the plugin looks for what it left (#784's look-back). When the plugin refused before sending, or the code host answered with a refusal, the agent hears it wasn't done; any other failure after the request may have gone out, a timeout or a 5xx, tells the agent "it may already be there; don't post it again", and a repeat that finds the earlier post shows its action line once; one after that line showed tells the agent the post is there already. A try refused before it was sent leaves the next a first try, and the look-back starts at the first try that may have gone out. The same words posted twice on purpose post once in a conversation; the user posts the second from the page.
- **One action line per write.** Each write comes back to the window as an `action` event of its turn: what it did, a link to where it shows, and, for a comment, a reply or a draft comment it added, Delete. Delete removes a posted comment through the code host's `deleteComment`, or a draft comment from the draft review. A code host without `deleteComment` keeps the link, and the line says to delete it there.
- **Never merge.** Merge is not one of the tools, and a call of any tool name that says merge is refused with `merge_refused`. Merging stays a confirmed action of the user's (ADR 0002), because it can't be undone and no action line can delete it.

## Considered options

- **Ask the user to confirm each write in the chat.** Rejected. The user already asked for the write in their message; a second click for each line makes the chat slower than doing it by hand, and the asks are there for reading. A write the user didn't want is deleted from its line.
- **Let the chat only draft, and post nothing.** Rejected. Replying to and resolving threads is most of what a reviewer asks for after reading, and a draft can't hold a reply or a resolve.
- **Let the window decide whether a draft comment may still run**, from the age of the call and the turn's `ended` event. Rejected. A call delivered late looks fresh to the window, and a Stop made while the stream was down sends no `ended` it will see, so the window added comments the agent had been told weren't added. The local API knows both, so it owns the claim.
- **Hold the writes behind ADR 0001's Undo window.** Rejected for the reasons ADR 0002 gives: comments that appear late confuse the people waiting on them.
- **Offer merge behind a confirmation.** Rejected. One misread instruction would merge code the user never approved, and the review page already has Merge one click away.
- **Let the chat approve and request changes, as the user asked.** Rejected (council round 1). A prompt-injected line in a description, a thread or a ticket could make the agent believe the user asked, and an approval is acted on by others without reading it. Finish review is one key away (R then Y).
- **Check Stop and revocation between a plugin's own requests.** Declined (council round 1). Ajour checks the turn, its head and the consent right before each plugin operation starts, with nothing awaited in between; an operation already started runs to its end, such as an Azure DevOps reply that first reads its thread and then posts, or a review that posts several comments. Stopping between a plugin's own requests would need a new plugin contract: a cancellation the plugin checks, and an answer for a write left half done. The window is one operation's length, and each write's action line still lets the user delete what it made.

## Consequences

- The consent the user gave for asks covers the chat: a message sends what an ask sends, the user's words, the code the agent reads and the threads, and nothing more. A chat regroup follows Regroup's rules (#794): it needs the consent that covers the pull request's description and linked tickets, and Ajour hands the agent those, as a regroup's turn quotes them, before it checks the guide's problem against them. That consent is checked for the agent that gets them: a regroup's turn is sent only to an agent allowed for the context, whichever agent Settings › Agents picked when it was asked for, and the chat's handoff asks again once Ajour read them.
- What the chat posts is the user's on the code host: the privacy policy and Deck's page say so, and that a deleted comment's earlier notifications stay with the people who got them.
- A plugin that implements `deleteComment` lets the chat's Delete work on that code host; the official plugins add it in #960.
